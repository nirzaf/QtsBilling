## Current architecture state (after QB-07 / QB-08 / QB-09 / QB-10 / QB-11 / QB-12 / QB-13 / QB-14 / QB-16 / QB-17 / QB-18 / QB-19 / QB-20 / QB-21 / QB-22)

- `QtsModels` — provider-neutral value objects (`Money`, `Quantity`, `CurrencyCode`, `ScaledDecimal`).
- `QtsBilling.Contracts` — wire DTOs (paging, customers, catalog, accounting, inventory, sales capture, sync envelopes, identity), canonical JSON fingerprinting, typed API clients (`CustomerApiClient`, `AccountApiClient`) and `ApiException`.
- `QtsBilling.Persistence.Postgres` — `BillingDbContext` (Identity-enabled), business and identity schema, with migrations for integrity guards, identity, ledger/sale idempotency, cash/refunds, invoice credits, purchasing, inventory valuation, tenant keys, native authorization, posted-document and period guards, onboarding, device command receipts, business settings, open-item payments, supplier bills, expense tax snapshots, partial refunds/credits, customer-credit balances, and credit-note idempotency.
- `QtsWebApp` — ASP.NET Core host on **PostgreSQL**: Blazor app + `/api/v1` (auth, customers, products, accounts, periods, journal entries, trial balance, locations, inventory movements/balances/reconciliation, POS sales, cash registers/receipts/refunds, invoices/credit notes, suppliers, purchase orders with receipts/returns, expenses, tax rates, discounts, reports (balance sheet, profit and loss, cash, stock, sales summaries), audit events, health), cookie sessions with permission policies, typed ProblemDetails/correlation ids, contract JSON options, OpenAPI in Development.
- **Sales (QB-09).** One request posts the sale, line snapshots, stock movements, payment, balanced journal and audit event atomically; `Idempotency-Key` + payload fingerprint receipts make retries safe (replay returns the stored sale; a changed payload is refused).
- **Cash drawers, receipts and refunds (QB-10).** Cash sales can name a register with an open drawer session; movements are audited with reasons; expected cash is derived from movements and close stores counted/variance. Card capture is disabled until a verified PSP exists. Receipts render from snapshots. Cash refunds can cover selected quantities over multiple requests, with restock or damaged-write-off disposition, incremental ledger entries, drawer movements, and `Idempotency-Key` replay protection.
- **Invoices and credits (QB-11).** Drafts are editable with server-computed totals; issuing allocates `INV-<year>-#####` inside the posting transaction and freezes snapshot lines. Payments allocate against the open balance with idempotency receipts; posted invoices are never edited. Multiple partial/full credit notes reference the original invoice, preserve line-level quantity/value snapshots, optionally restock inventory, and apply paid-invoice excess to customer-credit liability `2105`. Printable HTML invoice with DRAFT/VOID banners.
- **Purchasing, expenses and pricing (QB-12).** Purchase orders are commitments only; stock moves through idempotent receipts (`GRN-`) and returns (`PR-`) with quantity/cost snapshots validated under a row lock. Expenses post one balanced entry against cash/bank and reverse exactly once; tax rates are bounded exact decimals with a single default; discount definitions are validated (percentage 0-100, fixed non-negative, ordered window) before storage.
- **Reports from authoritative facts (QB-13).** Balance sheet, P&L, cash, stock and sales statements are computed per request from posted journal lines and inventory movements: no stored balances, base-currency-only, business-scoped responses (echoed ids), provisional offline money excluded by construction, and live tie-outs (sheet balanced, P&L = current earnings, cash = trial balance, stock = inventory balances).
- **Security, audit and recovery (QB-14).** API failures are typed ProblemDetails with stable codes and a correlation id (domain rules, 400/401/403/500; no stack/SQL leakage) and there is no database-writing error logger. Authentication outcomes are audited append-only with masked e-mails and request correlation, readable through the tenant-scoped `audit-events` feed (`audit.view`, Owner). Reset tickets are never logged; Data Protection keys can persist via `QTS_DATAPROTECTION_PATH`. Real `pg_dump` backups carry SHA-256 manifests, restore into a disposable database and reconcile (scripts + drill); the app role is DML-only and the static secret scan is clean.
- `QtsWebApp.Client` — browser talks to the API only; **no** database assemblies or credentials in the bundle (QB-15).
- `QtsBilling.Ui` — shared MudBlazor Razor Class Library (customer page + dialog, layout, nav) used by the web client and by the future MAUI host. It references only `QtsBilling.Contracts` + MudBlazor, consumes `ICustomerApiClient`/`IAccountApiClient`, declares no render modes and owns no assets; hosts register the RCL assembly for SSR/client routing and load MudBlazor + shared scoped CSS. QB-16 verified the live `/customers` render and an HTML-render smoke with stub interfaces (MAUI host build still blocked by the missing workload).
- `QtsBilling.Persistence.Sqlite` — device-local store (QB-17): one WAL SQLite file per device with a discardable cache group and a durable pending group (provisional sales, cash movements, outbox, inbox receipts, device profile, sync cursors); money/quantity are checked scaled `INTEGER` values, writes are serialized by one gate, startup blocks on a failed integrity check or an unknown/newer schema and snapshots the file before migrating. 20 temp-file tests cover atomic capture, rollback, idempotency, restart/cache-rebuild durability, crash recovery, integer comparisons and the v1→v2 upgrade with pending records. No web project may reference it; the MAUI host consumes it.
- `QtsBilling.Maui` — Windows desktop client (QB-18/QB-19): .NET 10 MAUI Blazor Hybrid host for `net10.0-windows10.0.19041.0`. It renders the shared `QtsBilling.Ui` components in a WebView2, owns the host assets, the device identity (GUID v7), the DPAPI-backed session and the offline-tolerant API adapters, opens the device-local SQLite store at startup and writes a secret-free startup report plus an API-call log. The shared point-of-sale view captures cash sales into the device store through `ILocalPosService` (the browser host registers a stub that refuses offline capture); the money rules live next to the store, the receipt is explicitly provisional and the pending queue survives restarts.
- `QtsWebApp/Features/Sync` — the idempotent sync-push handler (QB-20): `POST /api/v1/sync/operations` accepts a captured operation exactly once. The receipt row in `processed_operations` is written in the same transaction as the sale (the QB-09 posting path, extracted into `Features/Sales/SalePosting` and shared with the live POS endpoint), a replay returns the original outcome, a divergent body is a stable conflict, and the device, business and payload version are checked before anything is written.
- `QtsWebApp/Features/Sync` — the master-data change feed (QB-21): `GET /api/v1/sync/changes` returns the commit-ordered changes of a business. The feed row is written in the same transaction as the master-data write, the per-business revision is allocated by a row-locked increment, a deactivation is a tombstone, the projections are permission scoped, and a cursor past the server is answered with `RESYNC_REQUIRED`.
- Cash register, invoices, purchasing, expenses and reporting all run on PostgreSQL (QB-10…QB-14 done).
- Data migration (QB-23…QB-25) is an out-of-band effort importing historical data from an external source. No dual writes exist; the PostgreSQL path serves its own surface.
