# QB-40 — The composite tenant foreign keys: the exact scope, the data check and the wave plan

**Status: SPECIFIED AND PREPARED (not applied).** The scope is now exact, the existing data is proven
consistent, and the conversion is ordered into waves that can each be applied, verified and reverted
on their own. Applying the waves is the next step; it is a schema change of ~35 foreign keys and is
deliberately **not** half-applied.

## The rule (specification D02, finding F08)

> A relationship between business-owned rows must use `(id, business_id)` at both the foreign key and
> the principal key. A document's location, customer/supplier, variant, tax, account, session,
> source/reversal and allocation references must belong to that business.

The identity references (`users`, `roles`) stay single-column: a user is not tenant-owned.

## The exact scope (read from the database, not from the source)

**35 single-column business-owned foreign keys** remain. The parents already carry a unique
`(id, business_id)` index, so no new index is needed — only the keys have to use it.

| Wave | Parent (the principal key becomes `(id, business_id)`) | The dependants that must change with it |
|---|---|---|
| W1 | `sales` | `payments.sale_id`, `cash_register_movements.sale_id`, `sale_lines.sale_id`, `invoices.source_sale_id`, `sales.reversal_of_sale_id` |
| W2 | `journal_entries` | `journal_lines.journal_entry_id`, `credit_notes.journal_entry_id`, `refunds.journal_entry_id`, `expense_reversals.journal_entry_id`, `journal_entries.reversal_of_entry_id` |
| W3 | `business_locations` | `invoices.location_id`, `expenses.location_id`, `journal_lines.location_id`, `device_registrations.location_id`, `cash_register_sessions.location_id`, `purchase_orders.location_id`, `receipts.location_id` |
| W4 | `customers`, `suppliers` | `invoices.customer_id`, `sales.customer_id`, `expenses.supplier_id`, `purchase_orders.supplier_id`, `payments.*` |
| W5 | `product_variants`, `products` | `invoice_lines.variant_id`, `sale_lines.variant_id`, `inventory_movements.variant_id`, `products.*` (category, brand, group, unit, tax rate) |
| W6 | `accounts`, `accounting_periods`, `cash_register_sessions`, `device_registrations`, `expense_categories`, `invoice_sequences`, `purchase_orders`, `purchase_receipts`, `purchase_order_lines` | their dependants (accounts.parent_id, expense_categories.account_id, expenses.expense_category_id, journal_entries.accounting_period_id, payments.cash_register_session_id, processed_operations.device_id, audit_events.device_id) |

Each wave is one migration: drop the single-column key, add the composite key, and the model declares
`HasForeignKey(e => new { e.XId, e.BusinessId }).HasPrincipalKey(p => new { p.Id, p.BusinessId })`.
The wave order matters: a parent and **all** of its dependants change together, because a principal key
is unique per entity.

## The proof each wave must carry

1. **The database refuses a cross-tenant row.** A direct insert that points, for example, a payment of
   business A at a sale of business B must fail with a foreign key violation — not merely be filtered
   out by the application. The test writes the row with raw SQL and expects the database to refuse it.
2. **The application still works.** The whole suite (82 domain and PostgreSQL integration tests, 30
   device store tests) passes after the wave, and the existing data is unchanged.
3. **The wave is reversible.** Each wave is one migration with a `Down` that restores the previous key.

## Decisions recorded

- **D-70** — the tenant keys (task 05): every relationship between business-owned rows uses
  `(id, business_id)` at both ends, applied in waves in which a parent and all its dependants change
  together. The identity references stay single-column. The existing data was verified to be
  consistent (zero cross-tenant rows), so each wave is a constraint change and never a repair.

## Why it is not applied yet

A foreign key change of this size is a schema migration on the tables that hold the money, the stock
and the documents. Applying half of it would leave the database in a state where some relationships are
tenant-scoped and others are not — the exact defect the task exists to remove, but only half fixed and
harder to reason about. The waves are prepared so that each can be applied, verified against the real
PostgreSQL and reverted on its own.
