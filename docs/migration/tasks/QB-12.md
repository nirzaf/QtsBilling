# QB-12 — Purchasing, expense, tax and discount integrity

**Status: DONE (verified live on PostgreSQL 18.6).** Purchase orders are commitments that never move stock
or the ledger; stock changes only through receipts, each of which is one idempotent document with
quantity validation under a row lock. Expenses post exactly one balanced entry per expense, reversals are
append-only, and tax/discount definitions are bounded before they can be stored (F-18, spec §3.5/§3.8).

## Deliverables

| Area | Contents |
|---|---|
| Suppliers | `GET/POST/PUT/DELETE /api/v1/suppliers` with `purchasing.manage`; soft delete keeps purchase history; inactive suppliers cannot be picked for new orders. |
| Purchase orders | `POST /api/v1/purchase-orders` (number `PO-<year>-#####` allocated transactionally), draft `PUT`/`DELETE`, `POST /{id}/order`, `POST /{id}/cancel` (reason audited, refused once goods were received) and `GET /{id}` with ordered-vs-received quantities per line. Line snapshots (product name/SKU, unit cost, discount, tax) are frozen once the order leaves draft — the DB trigger `qts_purchase_order_lines_draft_guard` was **narrowed** so the only permitted change after draft is the receipt bookkeeping (`quantity_received`), backed by a strengthened check constraint `quantity_received <= quantity_ordered` (migration `HardenPurchaseOrderLineReceiptGuard`). |
| Receipts | `POST /api/v1/purchase-orders/{id}/receipts` with a required `Idempotency-Key`: one transaction locks the order row, validates every line against ordered minus received, allocates `GRN-<year>-#####`, writes the receipt + line snapshots, moves stock via `InventoryLedger` (movement type `PurchaseReceipt`, reference `purchase_receipt`/receipt-line id) and updates the order status (`Ordered → PartiallyReceived → Received`). A retried request returns the stored receipt instead of moving stock twice; over-receipt → `409 OVER_RECEIPT`; draft/cancelled orders cannot take deliveries (`409 PURCHASE_ORDER_NOT_OPEN`). |
| Returns | `POST /api/v1/purchase-orders/{id}/returns` (same idempotent path, `PR-<year>-#####`): validates against the received quantity, posts `PurchaseReturn` movements (negative delta, same cost snapshot), decrements received quantities and re-derives the order status. |
| Expenses | `GET/POST/PUT/DELETE /api/v1/expense-categories` (optional ledger account link, `expense_categories.account_id`); `POST /api/v1/expenses` with `Idempotency-Key` creates the expense and posts exactly one balanced entry — expense account debit (category account or standard `5000`) against `1000` cash or `1010` bank depending on `paidVia` (cash/cheque/bankTransfer/card; customer credit refused). `GET /api/v1/expenses` supports from/to/category/supplier/search filters. |
| Expense reversals | `POST /api/v1/expenses/{id}/reverse` (reason audited) posts the mirror entry inside one transaction and records an `expense_reversals` row (unique per expense, unique idempotency key). A second reversal → `409 ALREADY_REVERSED`; a replay with the same key returns the stored outcome. |
| Tax rates | `GET/POST/PUT/DELETE /api/v1/tax-rates` with `taxes.manage`: name unique per business, rate an exact decimal fraction bounded to `[0, 1]` with 6 decimal places (`numeric(12,6)`), at most one default per business (switching the default clears the previous one in the same transaction), soft delete. |
| Discounts | `GET/POST/PUT/DELETE /api/v1/discounts` with `discounts.manage`: percentage 0–100, fixed non-negative, at most 4 decimals, ordered validity window, scope (All/Product/Category/Customer), unique name per business, soft delete. Disallowed values are refused with `400 VALIDATION_FAILED`; duplicate names with `409 DUPLICATE_NAME`. |
| Schema | Migration `AddPurchasingReceiptsAndExpensePosting`: `purchase_receipts` (+ line table with quantity/cost snapshots), `expense_reversals`, `expenses.idempotency_key`/`payload_hash` (unique partial index), `expense_categories.account_id`. All tables carry tenant keys, FK-scoped relations and check constraints. |
| Error codes | `DUPLICATE_NAME`, `ALREADY_REVERSED`, `PURCHASE_ORDER_NOT_DRAFT`, `PURCHASE_ORDER_NOT_OPEN`, `OVER_RECEIPT` added to `ApiErrorCodes`; joining the existing `IDEMPOTENCY_KEY_REUSED`, `SAME_KEY_DIFFERENT_PAYLOAD`, `VALIDATION_FAILED`, `CONFLICT`. |

## Evidence (live host + PostgreSQL 18.6, `docs/migration/tasks/qb12-evidence.txt`)

| Check | Result |
|---|---|
| Tax rate `0.14` / `0.15` created | `201`; stored and returned exactly (`0.14`, `0.15`) |
| Out-of-range rate `1.5` | `400 VALIDATION_FAILED` |
| Duplicate rate name | `409 DUPLICATE_NAME` |
| Switch default to `0.15` | `200`; exactly one default afterwards (`count=1`) |
| Discount `10%` | `201`; `150%`, fixed `-5`, inverted window | `400 VALIDATION_FAILED` each |
| Create PO (2 lines? one line: 10 × 20.00, discount 5.00, VAT 14%) | `201`, `PO-2026-00007`, totals `subtotal 200 / discount 5 / tax 27.30 / total 222.30` |
| Stock right after creating the order | `onHand=0` — **a PO alone never increases stock** |
| Place the order, then edit it | `200` then `409 PURCHASE_ORDER_NOT_DRAFT` |
| Receive `6` of `10` | `201`, `GRN-2026-00003`; stock `6`; status `partiallyReceived` |
| Replay the same receipt key/payload | `200`, same receipt id; stock still `6` — **each receipt increases once** |
| Over-receipt (`5` of remaining `4`) | `409 OVER_RECEIPT` |
| Receive remaining `4` | `201`; stock `10`; status `received` |
| Return more than received (`11` of `10`) | `409 OVER_RECEIPT` |
| Return `2` | `201`, `PR-2026-00002`; stock `8`; status `partiallyReceived` |
| Movements for the fixture | `purchaseReceipt +6` / `+4`, `purchaseReturn -2`, all with cost `20.0000` and memo `GRN… / PO…` |
| Delivery against a draft order | `409 PURCHASE_ORDER_NOT_OPEN` |
| Cancel once / again | `200` / `409 CONFLICT`; draft delete `204` |
| Expense `120.50` cash | `201`, `JE-2026-00039`: `5000 debit 120.50` / `1000 credit 120.50` |
| Expense replay / changed payload | `200` same id / `409 SAME_KEY_DIFFERENT_PAYLOAD` |
| Expense paid by customer credit | `400 VALIDATION_FAILED` |
| Reverse expense, replay, second reversal | `200` (`JE-2026-00040`), `200`, `409 ALREADY_REVERSED` |
| Trial balance | cash `1000` and expense `5000` unchanged by the reversed expense (net zero); ledger stays balanced |
| PO list filter `status=partiallyReceived` | finds the order after the partial return |

## Decisions recorded

- **D-40** — purchasing: order vs receipt separation, snapshot lines, transactional numbering, idempotent
  receipts/returns, narrowed draft guard.
- **D-41** — expenses post one balanced entry per document with idempotency receipts and append-only
  reversals; tax rates are exact bounded decimals with a single default; discount definitions are validated
  before storage.

## Not included (tracked per task)

- Payment of purchase orders / supplier statements and ageing — the spec's QB-12 scope ends at goods
  receipt; AP settlement can reuse the payment patterns later.
- Manufacturing/restaurant purchasing models — explicit non-goal of QB-12.
- Partial receipt *IDs on the order line* beyond the receipt-line back-reference: each receipt line stores
  the `purchase_order_line_id` it fulfilled, and `purchase_receipt_lines` are append-only with their own
  identifiers as the spec requires; per-delivery notes are stored on the receipt header.
- Bulk import of legacy purchasing data — QB-23/QB-24 (needs an external legacy source).
