# QB-04 — Secure identity, business membership and OIDC

**Status: DONE (server core) — Identity on PostgreSQL, permission-checked tenant sessions and the
account-enrolment gate are verified end-to-end against the running host. The interactive OIDC/PKCE
device grant that the MAUI client needs is deferred to QB-22 (where the MAUI app is built); the web
app uses secure cookie sessions today.**

Decision: OPEN-7 default (self-hosted ASP.NET Core Identity). No external IdP is configured, so
OpenIddict remains the chosen provider for the device flow; nothing in the current surface invents a
new protocol (specification §3.4/QB-04 non-goals).

## Deliverables

| Area | Contents |
|---|---|
| Persistence | `User : IdentityUser<Guid>` with `DisplayName`, `IsActive`, `PasswordResetRequired`, `Version`, timestamps; `BillingDbContext : IdentityDbContext<User, IdentityRole<Guid>, Guid>`; identity tables mapped to snake_case (`users`, `roles`, `user_roles`, `user_claims`, `user_logins`, `user_tokens`, `role_claims`); migration `20261019111310_AddIdentity`. |
| Identity options | unique e-mail, password ≥ 12 with upper/lower/digit/symbol, lockout after 5 failures (15 min), token lifespan 2 h for reset/invitation tickets. |
| Claims | `QtsClaimsPrincipalFactory` adds `qts:business_id`, `qts:membership_role`, `qts:permission` (resolved from the role matrix) and `qts:password_reset_required`. A user without an active membership gets **no** business claim, so every tenant endpoint rejects the request. |
| Authorization | one policy per permission (`Permissions.*`); `PermissionAuthorizationHandler` requires the permission claim; nothing is inferred from the URL. |
| Sessions | `IdentityConstants.ApplicationScheme` cookie: `HttpOnly`, `SameSite=Strict`, 8 h sliding, 401/403 (never a redirect) for `/api/*`. |
| Endpoints | `POST /api/v1/auth/login`, `GET /api/v1/auth/session`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/password-reset/request`, `POST /api/v1/auth/password-reset/complete`. |
| Enrolment gate | New accounts are created with `PasswordResetRequired = true`; sign-in is refused with `403 PASSWORD_RESET_REQUIRED` until the ticket is completed. The reset request never reveals whether an account exists (unknown accounts also return 202). |
| Development bootstrap | `DevDataSeeder` (Development only) applies migrations and creates one owner account **with setup pending** — the gate is exercised locally exactly as in production. Production expects the ticket to be delivered out of band. |

### Role → permission map (server-side, re-checked per request)

| Role | Permissions |
|---|---|
| Owner | all |
| Manager | customers, products, inventory, sales, purchasing, expenses, invoices, accounting (post), reports, devices |
| Cashier | customers (read/write), products (read), sales (post), reports |
| Accountant | customers/products (read), accounting (post/close), invoices, expenses, reports |
| Viewer | customers/products (read), reports |

## Evidence (running host, PostgreSQL 18.6)

| Check | Result |
|---|---|
| Anonymous read/write to `/api/v1/customers` | `401` |
| Sign-in before enrolment completes | `403` + `code: PASSWORD_RESET_REQUIRED` |
| Reset ticket request (development) | `200` with one-time ticket; unknown account → `202` (no enumeration) |
| Complete enrolment with ticket → sign-in | `204`, then `200` session with `businessId`, `roles: ["Owner"]`, 15 permissions |
| Role downgraded to Viewer → read/write | read `200`, write `403` (permission policy, not UI) |
| Cross-business customer id | `404` `NOT_FOUND` (never a cross-tenant read/write) |
| Logout → session/list | `204`, then `401` |
| Raw-password lookup | gone: the web host no longer references `QtsServices.UserManagementService`; Identity verifies salted hashes |
| Secrets in the browser | no database driver, connection string or Mongo type in the WebAssembly bundle (`_framework` contains no `Mongo*`, `DnsClient*`, `Npgsql*` or `QtsServices*` assets) |
