# QB-20 — Server idempotent sync-push handler

**Status: DONE (endpoint, transaction, replay, conflict, authorization).** `POST /api/v1/sync/operations`
accepts the operations a device captured offline. Each operation is accepted **exactly once**: the receipt
row and the business effect are committed in one database transaction, a replay returns the original
outcome, the same operation id with a different body is a stable conflict, and an operation from another
business or from a device that is not enrolled is refused. The sale itself is posted with the QB-09 rules
- the device never decides price, tax, stock or the sale number.

## Deliverables

| Area | What was delivered |
|---|---|
| Endpoint | `POST /api/v1/sync/operations` (one operation) and `POST /api/v1/sync/operations/batch` (up to 50), both behind `sales.post`. The answer is a typed `SyncOperationReceipt` with the outcome, the stable error code, the server sale id and the posted reference. |
| Idempotency ledger | The receipt row lives in `processed_operations`, unique per `(business, device, operation)`. It is written **inside the sale transaction**, so a crash after the commit can never produce a second sale, and a retry finds the row and returns the original outcome. |
| Fingerprint | The server recomputes the canonical fingerprint of the payload with the shared `CanonicalJson` rules and compares it with the stored one. The same key with a different body is `409 SAME_KEY_DIFFERENT_PAYLOAD`; a body that does not match its own hash is `400 PAYLOAD_HASH_MISMATCH`. |
| One posting path | The sale posting of QB-09 was extracted into `SalePosting` and is used by both the live POS endpoint and the sync handler, so the accounting, inventory, payment, numbering and audit rules are never re-implemented. `SalePosting.PostSaleAsync` takes the optional receipt row and a commit hook, which is how the receipt and the sale end up in one transaction. |
| Server-authoritative facts | The device sends the facts it observed (variant, quantity, cached price, tax rate, cash); the server re-prices from the catalog, re-reads the tax rate, re-checks the stock, the drawer session and the accounts, and refuses a stale price or a missing tax rate. |
| Authorization | The operation must belong to the caller's business, and the device must be enrolled in that business and not revoked. The user must hold `sales.post`. The device id and the business id in the envelope are checked against the session. |
| Versioned payloads | Only `pos.sale.capture.v1` with payload version 1 is accepted; anything else is refused with a stable code instead of a guess. |
| Outcomes | `Posted` (committed, with the sale id and the posted reference), `NeedsReview` (a business rule refused it - the decision is remembered so a retry returns the same answer), `NotAuthorized`, `DeviceRevoked`, `UnsupportedPayloadVersion`, `TransientRetry` (the device keeps the operation in its queue) and `SameKeyDifferentPayload`. |
| Live smoke | `scripts/qb20-sync-push-smoke.cs` pushes one offline operation five times and prints the five documented answers. |

## Legacy items mapping

| Legacy concern | Resolution |
|---|---|
| The desktop client could not talk to the server | The device pushes its outbox to this endpoint; the server answers with a receipt the device stores (QB-22 wires the loop). |
| A retry could post the sale twice | The receipt row and the sale share one transaction; the replay returns the original sale id. |
| The device could decide the price | The server re-prices and refuses a price or tax rate that does not match the catalog (`INVALID_PRICE`). |

## Decisions recorded

- **D-49** — sync-push contract (QB-20): the server accepts an offline operation at
  `POST /api/v1/sync/operations` and answers with a typed receipt. The operation id is unique per
  (business, device, operation) and the receipt row is written in the **same transaction** as the sale, so
  "at least once" delivery can never produce "more than one" business effect. A replay returns the
  original outcome, the same key with a different body is a stable conflict, a refused business decision
  (for example insufficient stock) is remembered so a retry answers the same way, and a transient failure
  is reported as `TransientRetry` so the device keeps the operation in its queue. The sale is posted by the
  QB-09 path, which was extracted into `SalePosting` and is now shared by the live POS endpoint and the
  sync handler - the offline path never re-implements a business rule. The device's facts are inputs, not
  decisions: the server re-prices, re-checks the tax rate, the stock, the drawer and the permissions, and
  the device, the business and the payload version are all checked before anything is written.

## Not included (tracked)

- The device-side push loop, the backoff and the change feed that refreshes the device cache (QB-21/QB-22):
  the server side of the loop is ready and answers with a receipt.
- The device enrolment flow (the endpoint that issues an enrolment for a device) - the sync handler
  expects an enrolled, non-revoked device; the enrolment itself arrives with QB-22.
- Offline refunds, offline invoice issuance and offline card payments - explicit non-goals of this cutover.
- A change feed with revisions and tombstones (QB-21).
