# QB-23 / QB-24 / QB-25 — Historical data import (export, transform, load, reconciliation)

**Status: DONE (the chain is implemented and verified end to end). MongoDB is not a dependency of this
repository any more.** The import is a repeatable, read-only CLI, `QtsBilling.Migration`, that works from an
**exported, hash-verified snapshot** of the legacy system. The snapshot is produced once with the operator's
own tooling (outside this repository); the tool never talks to a legacy database, holds no driver and
carries no credential. The legacy MongoDB runtime is gone from the solution, and the repository has no
`MongoDB.*` dependency at all.

## What was built

| Task | What it does now |
|---|---|
| QB-23 inventory and export | `QtsBilling.Migration inventory` classifies every collection of a snapshot: the document count, the field types, the duplicate source ids and the credential-bearing fields. The tool verifies the snapshot against the **manifest hashes** before it reads a single document, so a tampered or half-exported snapshot is refused. The sensitive fields (passwords, salts, CVV, card numbers, tokens) are never exported and never appear in a log or a report. |
| QB-24 transform and load | `QtsBilling.Migration transform` maps every document onto the new schema with the **mapping file** (`docs/migration/mapping.sample.json`) - the mapping is data, so it is reviewed and corrected without touching the tool. The transform is deterministic: the target id is derived from the source identity (never a cast of a Mongo ObjectId), the numbers are parsed with the invariant culture, the documents are processed in source-id order, and a record that cannot be mapped is **quarantined with its source id** instead of being repaired. `QtsBilling.Migration import` loads the rows in the mapping order with an idempotent upsert, writes every mapping to the append-only `legacy_identifier_map` and refuses to overwrite a mapping that points somewhere else (a changed transformation needs a new version). A row that collides with an existing record or that would break a foreign key is quarantined and the import continues. |
| QB-25 reconciliation and reset plan | `QtsBilling.Migration reconcile` compares, per collection, the source count, the transformed count, the imported count (the rows this import owns, not the size of the table) and the quarantine reasons, lists every exception with its source id and writes a **signed** report: a SHA-256 over the canonical body plus an HMAC-SHA256 signature with the key from the environment. Without the key the report says `unsigned` - it is never silently "signed". A legacy value that has no counterpart in the new schema (an old customer balance, for example) is reported as a reconciliation exception and **blocks the go-live** until it is decided; it is never imported as a synthetic balance. The identity migration does not import credentials: the accounts are reset through the existing invite/reset flow. |

## Decisions recorded

- **D-55** — MongoDB is retired from the repository (QB-23/24/25): nothing in the solution, the packages or
  the runtime depends on a MongoDB driver any more; the legacy services are deleted and the historical
  import reads an exported, hash-verified snapshot instead of a live database. The tool therefore works
  without a legacy instance, and the snapshot - not a running legacy system - is the unit of record.
- **D-56** — the import contract (QB-23/24/25): the mapping is data, the transformation is deterministic
  and the load is idempotent. A source id maps to exactly one target id, the mapping history is append-only,
  a record that cannot be mapped is quarantined with its source id, a legacy value without a counterpart
  becomes a signed reconciliation exception that blocks the go-live, and the report is signed so that it
  cannot be edited unnoticed.

## Not included (tracked)

- The import of the **production** snapshot: the chain is proven, but the real data still needs a snapshot
  from the legacy environment and a reviewed mapping (the sample mapping uses the legacy field names of the
  removed model and must be aligned with the actual inventory before the real run).
- The identity migration of the real accounts: the import never carries credentials; the accounts are reset
  through the invite/reset flow during the cutover (QB-30).
