# QB-09 — Atomic idempotent server-side sale posting

**Status: DONE (verified live on PostgreSQL 18.6).** A sale is posted server-side before any receipt
exists: one request commits the sale, its line snapshots, the stock movements, the payment, a balanced
journal entry and the audit event in a single transaction. A retry with the same `Idempotency-Key`
returns the original sale instead of posting twice, and a changed payload under the same key is
refused (`F-05/F-14/F-16`, spec §3.1/§3.5/§4.6).

## Deliverables

| Area | Contents |
|---|---|
| Routes | `POST /api/v1/pos/sales` (post a sale), `GET /api/v1/pos/sales` (keyset-paged summaries), `GET /api/v1/pos/sales/{id}` (detail with snapshots + payments). |
| Idempotency receipt | Required `Idempotency-Key` header (1–64 chars). The canonical payload fingerprint (`RequestFingerprint`) is stored on the sale (`sales.idempotency_key`, `sales.payload_hash`) behind the unique partial index `ux_sales_business_idempotency_key`. |
| Replay semantics | Same key + same fingerprint → `200` with the **stored** sale (same id/number; no second stock movement, payment or journal). Same key + different fingerprint → `409 SAME_KEY_DIFFERENT_PAYLOAD`. A request refused before any write (validation/price/stock/payment) persists nothing, so its key stays reusable. |
| Price authority | The catalog price of the referenced variant is authoritative; a client-submitted unit price that differs is refused with `409 INVALID_PRICE` — the server never silently re-prices or accepts an unrecorded discount. |
| Tax | The stored rate (fraction 0–1) is applied per line and snapshotted (`tax_rate`, `tax_amount`); the effective-rate tolerance guard from QB-02 applies. |
| Stock | One `sale` movement per line, committed through the shared `InventoryLedger` in the same transaction; a would-be negative balance returns `409 INSUFFICIENT_STOCK` and rolls the whole sale back. Unit cost is snapshotted per line (`unit_cost_snapshot`) for COGS. |
| Payment | Exactly one confirmed payment per sale; the amount must equal the sale total (cash may over-tender via `cash_received`); a `card` payment without a processing reference is `409 PAYMENT_UNCONFIRMED` (no false success — F-07 stance); `customerCredit` requires a customer. |
| Ledger | One balanced entry, source `(Sale, saleId)`: DR cash/bank/AR for the total + DR COGS for the snapshotted cost; CR revenue (subtotal − discount) + CR tax + CR inventory. Number comes from `invoice_sequences` (`S-<year>-00005`) locked `FOR UPDATE` in the same transaction; the period must be open. |
| Audit | An `audit_events` row records the actor, business, sale id, number and total. |
| Immutability | Posted sales have no update/delete routes; the rows are the receipt of what happened. |
| Reads | Summaries (`saleId`, number, currency, totals, `postedAtUtc`, `provisional` always `false` on the server) and detail with line snapshots (product name, SKU, quantity, unit price, discount, tax rate/amount, line total, unit cost) plus payments. |

## Evidence (live host + PostgreSQL 18.6, `docs/migration/tasks/qb09-evidence.txt`)

| Check | Result |
|---|---|
| Submitted unit price ≠ catalog (`20.00` vs `25.50`) | `409 INVALID_PRICE` |
| Card payment without processing reference | `409 PAYMENT_UNCONFIRMED` |
| Nonexistent variant id | `400 VALIDATION_FAILED` |
| Oversell `999` against `20` on hand | `409 INSUFFICIENT_STOCK`; sale count `4 → 4`, on-hand still `20.000000` (nothing survived) |
| Post cash sale `3 × 25.50 − 1.50 = 75.00` | `201`, `S-2026-00005`, tax `0`, `provisional=false` |
| Replay the identical request (same key + payload) | `200`, same sale id and number; no duplicate effects |
| Same key, changed payload | `409 SAME_KEY_DIFFERENT_PAYLOAD` |
| Stock after the sale | `17.000000` (started `20`, sold `3`) |
| Sale detail | 1 line: qty `3`, unit price `25.50`, discount `1.50`, line total `75.00`, cost snapshot `18.00`; payment `Cash`/`confirmed` |
| Journal `origin=sale` | 1 entry per sale (7 entries across all smoke sales) |
| Trial balance | Cash Dr `1241.50`/Cr `100.00`; Revenue Dr `100.00`/Cr `1241.50`; Inventory Cr `774.00`; COGS Dr `774.00` — debits = credits per account |
| Race: two terminals sell the remaining `17` at the same instant | one `201`, one `409 INSUFFICIENT_STOCK`; final on-hand `0.000000`, never negative |
| Reconciliation after all traffic | `mismatchCount=0`, `totalOnHand=0` = `totalMovementSum=0` |

## Decisions recorded

- **D-34** — posting idempotency for sales (header + stored fingerprint, replay returns the stored sale,
  changed payload refused; at-least-once delivery, exactly-once effect).
- **D-35** — the sale posting facts (catalog price authority, single confirmed payment, journal mapping
  by seeded account codes, one transaction for all effects).

## Not included (tracked per task)

- Sale reversal route (`POST /api/v1/pos/sales/{id}/reversal`) — QB-10/QB-13 (uses the QB-07 reversal engine).
- Cash-register sessions, safe drops, X/Z reports and receipt output — QB-10.
- Split/multi-payment capture and card-terminal or PSP integration — QB-10 / OPEN-6 (card currently requires a processing reference; no PSP is built).
- Cost layers (FIFO/LIFO/AVCO) — COGS uses the movement's unit-cost snapshot until OPEN-3 / QB-12.
- **Interim inventory-finance boundary:** movements created directly through `/api/v1/inventory/movements`
  are not journalized (they record physical stock only); the sale path is the first workflow that posts
  inventory-related journals. Purchases/adjustment capitalization and expense/tax integrity land with
  QB-12, so during the interim the Inventory account reflects sales credits only. This is deliberate:
  no invented offset account is used until QB-12 defines the purchasing side.
- Offline provisional sales, device receipts and sync push — QB-19/QB-20 (device rejections become
  `processed_operations` receipts there).
