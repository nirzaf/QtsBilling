# QB-30 — production cutover admission and execution

**Status: implemented and harness-tested; the production run is NOT EXERCISED.** The production
cutover is gated by the business owner's real environment, evidence and approval manifest. No test or
rehearsal in this repository has executed the cutover against a production target.

## Current implementation (Task 21)

`scripts/qb30-cutover.ps1` has two strictly separated modes:

- **Admission** is read-only. It creates no backup, starts no host and sends no auth request.
- **Execute** performs the approved writes only after admission and a second evidence check.

The manifest (`schema: qts-production-approval-v2`) is signed with HMAC-SHA256 and binds:

- environment, server, database and business ids;
- approved device ids;
- release commit and migration head;
- native package, reconciliation report, backup drill and G7 approval SHA-256 hashes;
- approved exception ids and an expiry.

One owner-held codeword is read from `QTS_CUTOVER_CODEWORD` and checked as a SHA-256 against the
manifest. There is no second caller-supplied comparison value.

## Ordered execution

1. Admission: manifest signature, target binding, hashes, database/schema, package validation,
   reconciliation verifier, drill, G7, identities, devices and integrity checks.
2. Re-verify the manifest and every evidence hash immediately before the first write.
3. Fresh verified backup.
4. Start the host and verify health.
5. Native package import into the disposable/approved target.
6. Native reconciliation and signed verification.
7. Owner identity reset.
8. Smoke.
9. Final integrity: ledger balance, stock detail and value, tenant ownership, invoice uniqueness,
   journal balance and non-negative openings.

Any failure stops the run; a failed import never reaches reconciliation, identity reset or smoke.

The harness proves the production script's control flow without touching a real target. It does not
prove the production environment, signatures, credentials, backup destination, DNS/TLS or owner
approval; those remain owner-gated.

## Stop / fix-forward

- **Stop**: a failed gate leaves the target untouched before execution, or stops after the last
  committed step during execution. No destructive rollback is attempted.
- **Forward**: correct the evidence or environment, re-sign the manifest, re-run admission and execute.
- **Never**: a blind rollback to a retired source or deletion of archived backups.
