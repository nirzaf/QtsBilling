# QB-21 — Server master-data change feed

**Status: DONE (feed, revisions, tombstones, resync decision).** Every master-data write now appends a
change row **in the same database transaction** as the write that caused it, and the per-business revision
is allocated by a row-locked increment inside that transaction. A device walks the feed with the compound
`(revision, ordinal)` cursor and therefore sees every committed change exactly once, in the order it was
committed. The feed is tenant scoped and permission scoped, and a cursor that points past the server is
answered with a `RESYNC_REQUIRED` decision instead of a silent gap.

## Deliverables

| Area | What was delivered |
|---|---|
| Change writer | `Features/Sync/SyncChangeWriter.cs`: the revision is allocated with `INSERT … ON CONFLICT DO UPDATE … RETURNING revision` (the row lock serializes the writers), the ordinal is the next one inside that revision, and the change row is added to the same `DbContext`, so it commits with the business write. |
| Transaction | `Features/Sync/SyncTransaction.cs` runs a master-data write and its feed row in one transaction, opened through the configured execution strategy - a transient database failure retries the whole unit instead of leaving the feed behind the business change. |
| Projections | `Features/Sync/SyncProjections.cs`: the product projection (with its sellable variants and prices), the customer projection and the stock projection. They carry the facts the offline screens need and never a secret. |
| Emission points | Product create, product update, variant update, customer create, customer update, customer deactivation (a **tombstone**) and every inventory movement (the stock balance) - the last one at the single choke point `InventoryLedger.ApplyAsync`, so a sale moves the stock and the device learns about it in the same transaction. |
| Feed API | `GET /api/v1/sync/changes?afterRevision=&afterOrdinal=&limit=` behind `products.read`. It returns a `SyncChangesPage` with the changes, the next cursor, `hasMore`, the schema version and the resync decision. A caller without `customers.read` never sees the customer projections. |
| Resync decision | A cursor that points past the current revision means the device and the server disagree about the history: the answer is an empty page with `resyncRequired = true` and the current revision, so the device re-pulls the baseline instead of missing changes silently. |
| Live smoke | `scripts/qb21-change-feed-smoke.cs` writes a product, a customer, a deactivation and an opening movement, then walks the feed from the beginning, from a cursor in the middle and with a cursor past the server. |

## Legacy items mapping

| Legacy concern | Resolution |
|---|---|
| The device had no way to learn about a price or a stock change | Every master-data write emits a projection; the device pulls it with the cursor. |
| A device that was offline for a long time could silently miss updates | The cursor is explicit, the order is the commit order, and a cursor the server cannot explain is answered with `RESYNC_REQUIRED`. |
| Deleted reference data would stay on the device | A deactivation is a tombstone in the feed, so the device drops the record. |

## Decisions recorded

- **D-50** — change feed contract (QB-21): a master-data write and its feed row are one database
  transaction, and the per-business revision is allocated inside that transaction by a row-locked
  increment, so the feed order is the commit order and a device that walks the `(revision, ordinal)` cursor
  sees every committed change exactly once. The projections carry only what the offline screens need
  (product with its variants and prices, customer, stock) and never a secret; a deactivation is a tombstone.
  The feed is tenant scoped and permission scoped - a caller without `customers.read` never sees the
  customer projections - and a cursor that points past the server is answered with `RESYNC_REQUIRED` instead
  of a silent gap. The write paths run through the configured execution strategy, so a transient database
  failure retries the business write and its feed row together. The retention window (how long a change row
  is kept before an old cursor must re-pull) lands with the operational work in QB-27.

## Not included (tracked)

- Change rows for the accounting, invoicing and purchasing master data: the first cutover syncs the
