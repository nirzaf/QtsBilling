# QB-44 — Posting belongs to one open period, and closing serializes with posting (specification task 10)

**Status: DONE and EXERCISED against real PostgreSQL.** Finding F20 is closed in `readiness.md`.

## What was built

| Piece | Where | Behaviour |
|---|---|---|
| Required covering period | `Features/Accounting/LedgerWriter.cs`, `ApiErrorCodes` | A posting with no covering period fails closed with `409 ACCOUNTING_PERIOD_MISSING`; the entry is never stored with a null `AccountingPeriodId`. |
| Shared lock on posting | `LedgerWriter` | While posting, the covering period row is read `FOR SHARE` inside the caller's transaction. |
| Exclusive lock on close | `Features/Accounting/AccountingEndpoints.cs` (`ClosePeriodAsync`) | Closing runs in one transaction, reads the period `FOR UPDATE`, rechecks its status, and only then sets it `Closed`. A posting that started first makes the close wait; a close that started first makes the posting wait and then see `Closed`. |
| Period integrity | `20261020145535_AccountingPeriodAndPostingIntegrity` | Periods cannot overlap. Once a period is not `Open`, its dates cannot change and it cannot be moved back to `Open` by an ordinary update; only the explicit close workflow changes the status. |
| Journal entry write | `LedgerWriter` | The entry is saved as `Draft`, its lines are inserted, then it becomes `Posted`, all in the caller's transaction. The existing deferred balance trigger still evaluates at `COMMIT`. |

## The evidence (against real PostgreSQL)

`TestQtsBilling/Integration/PeriodPostingTests.cs`:

| Test | Proves |
|---|---|
| `T10_01_a_posting_outside_every_period_is_refused` | A journal entry dated before every period returns `409` with `ACCOUNTING_PERIOD_MISSING`; nothing is stored. |
| `T10_02_a_closed_period_refuses_posting` | After the real close endpoint closes business B's period, a posting in that period returns `409 ACCOUNTING_PERIOD_CLOSED`; closing the same period again is also `409`. |
| `T10_03_overlapping_periods_and_reopening_are_refused_by_the_database` | An overlapping period insert is refused with `23514`; a closed period cannot be updated back to `Open`. |
| `T10_04_posting_serializes_on_the_period_row_with_closing` | While a session holds `SELECT ... FOR UPDATE` on the period (what close takes), the posting remains blocked; after the lock is released it completes with `201`. |

The whole suite passes: **107 tests**.

## What remains

- The serialization test proves the conflict and the wait deterministically, but it is not a
  high-concurrency stress test; the lock mode is the guarantee, not timing luck.
- A period can only be deleted while it is open and has no posted entries; the database enforces that.
  The API does not expose period deletion, and the retention rule is still a finance decision (B03).
- The close workflow does not yet compute or post a year-end closing entry; task 10 is the integrity of
  the close boundary, not the closing accounting.
