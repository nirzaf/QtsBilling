# QB-08 — Transactional authoritative inventory

**Status: DONE (verified live on PostgreSQL 18.6).** On-hand stock changes only together with an
append-only movement in one transaction; concurrent issues cannot oversell, replays cannot double-count and
balances always equal the movement sum (F-02/F-12).

## Deliverables

| Area | Contents |
|---|---|
| Locations | `GET /api/v1/locations` (per-business, `includeInactive`). |
| Balances | `GET /api/v1/inventory/balances?locationId&search&cursor&pageSize` joins variant + location, search on name/SKU/barcode, keyset cursor paging. |
| Movements | `GET /api/v1/inventory/movements?variantId&locationId&cursor&pageSize` (append-only history), `POST /api/v1/inventory/movements` applies one movement + balance change atomically. |
| Sign policy | Receipts (`opening`, `purchaseReceipt`, `saleReversal`, `transferIn`) require positive quantities, issues (`purchaseReturn`, `transferOut`) negative; `stockAdjustment` accepts either. `sale` is refused here — sales post through QB-09. |
| No oversell | The balance row is locked `FOR UPDATE`; a change that would go below zero returns `409 INSUFFICIENT_STOCK`. Two concurrent requests for the last unit produce exactly one `201` and one `409`. |
| Authorized negative | `allowNegative: true` is accepted only for `stockAdjustment` **and** requires a memo (the authorization + reason trail); everything else stays non-negative. |
| Idempotency | Unique key `(business, reference_type, reference_id, movement_type)`; replays return `409 IDEMPOTENCY_KEY_REUSED` naming the existing movement. |
| Reconciliation | `GET /api/v1/inventory/reconciliation` compares every balance with `SUM(quantity_delta)` and reports totals; mismatches are a defect the database forbids. |
| Transfers | Draft transfers are created with `Idempotency-Key`; source dispatch and destination receipt lock the transfer, call `InventoryLedger`, preserve movement valuation, and post 1200/1210 journal legs atomically. Both locations are checked against business membership access; immutable database guards prevent terms and valuation from changing after posting. |
| Cycle counts | `POST /api/v1/inventory/stock-counts` freezes active stock-tracked variants and expected quantity/cost; expected values stay hidden until finalization. `PUT /{id}/lines` submits the complete blind count; approval requires `inventory.adjust` and `accounting.post`, reconciles current stock under row locks, and posts 1200/5200 only for valued variances. |
| Catalog spine | Minimal products API (`GET/POST /api/v1/products`, `PUT /{id}`, `PUT /{id}/variants/{variantId}`) creates each product with its default variant so inventory and sales always reference concrete variants; per-business SKU/barcode uniqueness (`409 DUPLICATE_SKU`). |
| Transactions | Movement + balance commit inside `CreateExecutionStrategy()` (the Npgsql retrying strategy), clearing the change tracker per attempt. |

## Evidence (live host + PostgreSQL 18.6, `docs/migration/tasks/qb08-evidence.txt`)

| Check | Result |
|---|---|
| Product + default variant | `201` (`sellingPrice 25.5000`, variant created and linked) |
| Duplicate SKU | `409 DUPLICATE_SKU` |
| Opening `+10` | `201`, balance `10` |
| Replay of the same reference | `409 IDEMPOTENCY_KEY_REUSED` |
| Adjustment `−4` | `201`, balance `6` |
| Oversell `−10` | `409 INSUFFICIENT_STOCK` |
| Authorized `−1` with `allowNegative` + memo | `201`, balance `5` |
| Race: two simultaneous `−5` (the whole remaining stock) | one `201`, one `409`; final on-hand `0` |
| Reconciliation | `mismatchCount=0`, `totalOnHand=0.000000` = `totalMovementSum=0.000000` |
| Cross-business product id | `404 NOT_FOUND` |
