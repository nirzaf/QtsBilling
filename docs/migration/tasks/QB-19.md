# QB-19 — Offline cash-only sale capture

**Status: DONE (desktop capture, provisional receipt, pending queue).** The Windows desktop client can now
sell while the server is unreachable: the cashier picks items from the cached catalog, collects cash, and
the sale is committed **atomically** into the device-local store as a draft + fixed-price lines + a cash
movement + an outbox operation. The device shows a clearly **provisional** receipt with a provisional
reference - never a sale or invoice number - and lists everything that is still waiting for the server.
A capture that is not durably stored is never reported as a success, and the same operation id can never
create two operations.

## Legacy items mapping

| Legacy concern | Resolution |
|---|---|
| The prior desktop client only sold online | The desktop client sells from a local cache into a local queue; the server decides what happens when the operation arrives (QB-20). |
| Cash receipts looked like final receipts | The local receipt is marked `PROVISIONAL`, states that the sale number is assigned by the server, and shows a provisional reference instead. |
| A double click could create two sales | The checkout keeps one operation id until the capture is accepted, the button is disabled while it runs, and the store refuses a second operation with the same id and a different body. |

## Decisions recorded

- **D-48** — offline capture boundary (QB-19): the point of sale lives in the shared library and reaches
  the device store only through `ILocalPosService`; the browser host registers a stub that refuses
  offline capture instead of pretending. A capture is accepted only after the draft, its lines, the cash
  movement and the outbox row are committed in one SQLite transaction; the money rules (positive total,
  cash covers the total, checked scaled integers) live with the store, and the canonical payload is
  fingerprinted with the shared `CanonicalJson` rules so the server can compare the same body when the
  operation arrives. The checkout keeps one operation id until the capture is accepted, so a double click
  cannot create two operations, and the same id with a different body is a conflict, not a second sale.
  The offline permission is limited on purpose: a signed-in account with `sales.post`, an enrolled
  business, location and cash register - nothing else, and the server re-checks all of it when the
  operation is pushed. The receipt is explicitly provisional and never carries a sale or invoice number.
  The catalog endpoint now carries the product's tax rate and tax type, because a device cannot cache a
  sellable price without the tax snapshot; the change feed with revisions replaces this pull in QB-21.

## Not included (tracked)

- Pushing the captured operations to the server (QB-20) and the change feed that refreshes the cache
  (QB-21): the device already stores everything the push needs (canonical payload, fingerprint, device,
  business, location, register, user).
- The OIDC/PKCE device flow and the sync coordinator (QB-22).
- Offline card payments, offline invoice issuance, offline refunds and offline master-data editing -
  explicit non-goals of this cutover; only cash-only capture is allowed offline.
- A barcode scanner integration and multi-location switching on the device.
