# QB-11 — Immutable invoice and credit workflow

**Status: DONE (baseline live verification; partial-credit extension verified by focused PostgreSQL integration tests).** Invoices run the full lifecycle: editable drafts, transactional issuance (row-locked number allocation), payment allocation against the open balance, void for unpaid invoices and multiple line-level partial or full credit notes that reference the original. Posted financial terms are never edited: every correction is a new document and the snapshots that produced the printout never change (F-10, spec §3.7).

## Deliverables

| Area | Contents |
|---|---|
| Drafts | `POST /api/v1/invoices` creates a draft (no number yet); `PUT /{id}` replaces the lines and recomputes totals; totals/tax are computed server-side from the submitted lines (`unitPrice`, `discountAmount ≤ line gross`, `taxRate 0..1`), so a client can never post an inconsistent total. `DELETE /{id}` removes a draft only. |
| Snapshot lines | Every line stores `productNameSnapshot`, `skuSnapshot`, quantity, unit price, discount, tax rate/amount and line total. A line with a `variantId` snapshots the catalog name/SKU at save time; ad-hoc service lines require an explicit name. Draft lines are replaceable; once issued they are never touched — a later product rename or price change cannot alter a historical invoice. |
| Issuing | `POST /{id}/issue`: inside one transaction the invoice row is locked (`FOR UPDATE`), the number is allocated from `invoice_sequences` (row-locked, `INV-<year>-#####`), the receivable entry is posted (`1100` debit; `4000` revenue credit; `2100` tax credit) and the invoice becomes `Issued`. The partial unique index `ux_invoices_business_number` makes duplicate numbers impossible even under concurrency. |
| Immutability | A non-draft invoice refuses `PUT` and `DELETE` with `409 INVOICE_NOT_DRAFT` ("posted invoices are never deleted / edited"); corrections go through void or a credit note. `InvoiceLine` left the append-only entity list because draft lines are replaceable by design — the immutable snapshot is created at issuance and the API is the enforcement point (D-38). |
| Void | `POST /{id}/void` (reason required, audited): only for `Issued`/`PartiallyPaid` with **no confirmed payments** (`409 INVOICE_HAS_PAYMENTS` otherwise); posts the balanced reversal of the invoice entry, sets `Void` and keeps the number and history. |
| Payments | `POST /{id}/payments` allocates a confirmed payment against the open balance (overpayment → `400 VALIDATION_FAILED`): cash, cheque and bank transfer (card → `409 PAYMENT_METHOD_DISABLED`, D-36; cheque/bank require a reference). One transaction locks the invoice, re-checks the balance, inserts the `payments` row, posts `DR cash 1000 / CR receivable 1100` (cheque/bank via `1010`) and moves the status `Issued → PartiallyPaid → Paid`. Cash may name a register with an open drawer session, which also records a drawer `cashIn` movement. `Idempotency-Key` + payload fingerprint (unique partial index `ux_payments_business_idempotency_key`) make retries safe: replay returns the stored payment (200); the same key with a changed payload → `409 SAME_KEY_DIFFERENT_PAYLOAD`. |
| Credit notes | `POST /{id}/credit-notes` (reason and `Idempotency-Key` required): partial or full quantities from issued invoice lines, numbered `CN-<year>-#####`, with append-only `credit_note_lines` snapshots. Cumulative credited quantity cannot exceed the issued line quantity. Same key/payload replays with `200`; reusing a key for different content returns `409 SAME_KEY_DIFFERENT_PAYLOAD`. Each note posts the incremental sales-return, tax, receivable/customer-credit, and optional inventory/COGS entries. Credit applied beyond the unpaid receivable is credited to customer-credit liability `2105`, keeping `BalanceDue` at zero. An unpaid invoice becomes `Void` only when fully credited; paid invoices remain `Paid` while any excess is a customer credit. |
| Printable document | `GET /{id}/print` renders a self-contained HTML invoice from the stored snapshots with a status banner: `DRAFT — NOT AN ISSUED INVOICE`, `ISSUED`, `PARTIALLY PAID`, `PAID IN FULL` or `VOID — NOT PAYABLE`, plus payment rows and the credit-note block. Every value is HTML-encoded. |
| Permissions | `invoices.manage` (create/edit/delete drafts, void, credit) and existing `invoices.issue` (issue, read, print, payments). Owner: all; Manager and Accountant: both. |
| Contracts | `QtsBilling.Contracts/Invoices/InvoiceDtos.cs` — `InvoiceState` wire enum (bridged in memory per D-31), save/detail/payment/credit DTOs. New error codes: `INVOICE_NOT_DRAFT`, `INVOICE_NOT_ISSUED`, `INVOICE_HAS_PAYMENTS`, `INVOICE_ALREADY_CREDITED` (plus existing `DUPLICATE_INVOICE_NUMBER`). |
| Schema | `20261020192550_AddPartialCreditNotes` adds line snapshots, invoice-line stock/cost snapshots, and backfills historical credit notes; `20261020193218_AllowCustomerCreditBalances` keeps paid invoice balances non-negative; `20261020193632_AddCreditNoteIdempotency` adds replay protection. Credit-note numbers remain unique, while multiple notes per invoice are allowed. The original `20261019124428_AddCreditNotesAndInvoiceSupport` migration also added payment idempotency and the partial invoice-number index. |
| Catalog fix | `PUT /api/v1/products/{id}` no longer reports `DUPLICATE_SKU` when a product keeps its own existing SKU (the variant check now excludes the product's own variants), which the "rename after issue" acceptance depends on. |

## Baseline evidence (live host + PostgreSQL 18.6, `docs/migration/tasks/qb11-evidence.txt`)

This table records the original one-full-credit implementation. Its credit-note rows are superseded by the partial-credit extension. `TestQtsBilling/Integration/PartialCreditNoteTests.cs` verifies partial and cumulative quantities, replay safety, full-credit final state, inventory restock, paid-invoice customer credit, and the 100% tax-rate compatibility case against the isolated PostgreSQL fixture.

## Decisions recorded

- **D-38** — invoice lifecycle and immutability rules (draft editing, transactional numbering, void/credit,
  no cash payout for customer credit balances yet).
- **D-39** — invoice payment allocation rules (methods, balance enforcement, drawer link, idempotency
  receipts on `payments`).

## Not included (tracked per task)

- Multi-invoice credit allocation — one credit note continues to reference exactly one original invoice.
- Cash payout of a customer credit balance — excess is recorded as a liability in `2105`; this workflow does
  not initiate a cash payout.
- Invoice PDF/email delivery — the printable HTML endpoint is ready; delivery channels arrive with QB-27
  packaging and the MAUI shell with QB-18.
- E-invoicing/cross-border formats — explicitly a non-goal of the spec for this task.
- Legacy invoice data import — QB-23/QB-24 (needs an external legacy source).
