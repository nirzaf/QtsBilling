# QB-16 — Extract shared MudBlazor Razor components

**Status: DONE for the web host and the platform-injection contract; the MAUI host build remains blocked by
the missing `maui-windows` workload (D-25).** The customer page, its dialog, the edit model, the layout and
the navigation menu now live in a new Razor Class Library, `QtsBilling.Ui`. The library depends only on
`QtsBilling.Contracts` and MudBlazor: it carries no database, HTTP-host or server-only reference, no
`@rendermode` directive, and every host injects its own API-client implementation. The same component
renders in the web host at `/customers` and in a host-independent HTML renderer with stubbed feature
interfaces.

## Deliverables

| Area | What was delivered |
|---|---|
| New shared UI library | `QtsBilling.Ui` (Razor Class Library, `net10.0`) with `MudBlazor` 9.11.0 and a single project reference to `QtsBilling.Contracts`. No `QtsWebApp`, persistence, EF Core, Npgsql or database-driver reference may enter it (verified from the compiled assembly references and by the browser bundle scan). |
| Components moved | `Customers.razor` + code-behind, `AddCustomerDialog.razor`, `CustomerEditModel`/`CustomerRow`, `MainLayout.razor` (+ scoped CSS) and `NavMenu.razor` (+ scoped CSS). They were moved with `git mv`, so history is preserved. |
| API-only logic separated | The components consume the existing feature interfaces `ICustomerApiClient` and `IAccountApiClient` from `QtsBilling.Contracts`; no component performs HTTP, storage or database access itself. The web client keeps the HTTP implementations; a MAUI host will register its own implementations (OIDC/device-grant per QB-22). |
| Host wiring | The web client references `QtsBilling.Ui`, discovers its route through `AdditionalAssemblies`, uses `QtsBilling.Ui.Layout.MainLayout` as the default layout and keeps the shell-specific Login/Home pages. The server host registers the RCL assembly with `MapRazorComponents(...).AddAdditionalAssemblies(...)` so deep links such as `/customers` resolve during static SSR as well as after WASM hydration. |
| Host-owned assets | MudBlazor CSS/fonts/JS moved out of `NavMenu.razor` into the host shell (`App.razor`); the RCL scoped-CSS bundle is linked from the host at `_content/QtsBilling.Ui/QtsBilling.Ui.bundle.scp.css`. The future MAUI `index.html` performs the same host step, so no shared component loads host assets. |
| Render-mode compatibility | No shared component declares a render mode. The web host keeps `InteractiveAuto` at the `Routes` level (a host decision); a `BlazorWebView` host can render the same components statically/interactively without component-level mode conflicts. |
| Empty state / validation | The customer table now declares an explicit `NoRecordsContent` state ("No customers yet. Add a customer or adjust the search.") instead of an unexplained blank grid. The add dialog keeps `Required="true"` on the name and disables Save while the name is blank; MudBlazor supplies keyboard-operable controls and validation styling. |
| Platform-injection smoke | New `QtsBilling.Ui.Smoke` console harness: renders the shared page with an `HtmlRenderer`, a stub `ICustomerApiClient`, stub `IAccountApiClient`, stub `NavigationManager`/`IJSRuntime` and MudBlazor services, then asserts the route, headings, search/add/refresh controls, empty state, table headers and the absence of data-access references. This is the contract a MAUI host satisfies. |

## Legacy items mapping

| Legacy concern | Resolution |
|---|---|
| Desktop/WASM-specific page markup with HTTP calls inline | The shared page renders from `ICustomerApiClient`; each host supplies the implementation. |
| Duplicated pages between web and future desktop | The customer page/dialog/layout/nav exist once in `QtsBilling.Ui`; hosts contain only shell concerns (login/session UX, asset registration, router assembly registration). |

| Direct DB access from UI | The RCL assembly references only `QtsBilling.Contracts` and MudBlazor; the browser bundle still contains no persistence/EF/Npgsql assembly. |

## Decisions recorded

- **D-45** — shared-UI boundary (QB-16): reusable MudBlazor components live in `QtsBilling.Ui` and depend
  only on `QtsBilling.Contracts` + MudBlazor. Components consume feature interfaces, never HTTP, storage or
  a database. Hosts own render modes, MudBlazor assets, router/assembly registration and session UX; shared
  components may not declare `@rendermode` or reference server-only namespaces. Both the server endpoint
  table and the client router must register the RCL assembly, otherwise deep links 404 during SSR even
  though client-side navigation works. The MAUI host remains blocked by the missing `maui-windows` workload
  (D-25); the HTML-render smoke is the acceptance evidence until QB-18 can host the same components.

## Not included (tracked)

- The .NET MAUI host itself (QB-18/QB-19) — blocked by the unavailable `maui-windows` workload.
- New pages beyond the moved customer/layout/nav surface, a new design system, or duplicating pages per
  platform (spec non-goals).
- Device authentication UX for MAUI (OIDC/PKCE, QB-22); the current shared Login page remains host-specific
  in the web client until that task defines the device flow.
