# QB-37 — The stock balance is race-safe and negative stock is prohibited (F17/F18)

**Status: DONE (both halves of the finding are closed and proven against the real PostgreSQL).**

This is task 14 of the *SMB Completion and Production Hardening* specification.

## What changed

### F17 — the balance row and the deferred guard

| Before | After |
|---|---|
| A missing balance row was created as a **tracked entity**. Two concurrent movements on a variant without a balance both believed they created it, and the loser failed late with a uniqueness error instead of serializing on the row. | The balance row is created with a **scoped database upsert** (`ON CONFLICT DO NOTHING`) and only then **locked** (`FOR UPDATE`). The transactions serialize on the row; the insert is a no-op when the row already exists. |
| The deferred balance guard compared the **snapshot of the trigger event** (`v_row := NEW`) with the final movement sum. A row that was created and then updated in the same transaction was judged by the value it had *when it was inserted* (zero) instead of the value it ended with — so a perfectly correct first movement was refused. | The deferred guard reads the **current persisted state** and compares it with the movement sum (specification D04). The applied migration stays untouched; the new migration `20261020082901_FixDeferredInventoryBalanceGuard` replaces the function. |

### F18 — the negative-stock policy

The API offered an `AllowNegative` escape hatch for stock adjustments while the database forbids a
negative balance: the application and the database disagreed, and the override could only ever end in a
constraint violation.

- The option is **removed** from the contract (`RecordMovementRequest`), from the validation and from
  the ledger.
- `InventoryLedger.ApplyAsync` no longer takes an `allowNegative` flag: **negative stock is prohibited
  in this release, adjustments included**, and the refusal carries the on-hand and the requested
  change.
- The database check and the application now say the same thing.

`TestQtsBilling/Integration/InventoryConcurrencyTests.cs` — the real host, the real PostgreSQL:

| Case | Result |
|---|---|
| T14.01 — two concurrent movements on a variant **without** a balance | both are accepted, there is **exactly one** balance row, it carries both movements (3) and the movements tie to the balance. |
| T14.02 — a movement that would make the stock negative | refused with `409`, and the balance is unchanged (5). |

## Decisions recorded

- **D-66** — the stock balance and the negative-stock policy (task 14): the balance row is created
  with a scoped database upsert and only then locked, so concurrent movements serialize on the row;
  the deferred balance guard reads the current persisted state instead of the snapshot of the event
  that queued it; and negative stock is prohibited everywhere — adjustments included — so the
  application and the database agree.
