# QB-14 — Security, structured audit and real backup/restore

**Status: DONE (verified live on PostgreSQL 18.6).** The legacy failure modes this task targets are
structurally absent from the new host: there is no error logger that writes to the database, no static-IV
AES helper, no backup "metadata" pretending to be a backup, and no API error path that returns an empty
list or an HTML page instead of a typed failure. Real `pg_dump` backups are restored into a disposable
database and reconciled in the evidence below.

## Deliverables

| Area | What was delivered |
|---|---|
| Typed failures, no recursive logger | `ApiExceptionMiddleware` (new) turns unhandled `/api` exceptions into `application/problem+json` with `INTERNAL_ERROR` and a `traceId`; malformed bodies remain typed `400 VALIDATION_FAILED`; leaked domain rules keep their precise code. Logging is best-effort and **never** writes to the database — a failing sink is caught and cannot recurse, replace the response or turn a typed failure into an unhandled exception. Cookie auth now returns typed `401 UNAUTHENTICATED` / `403 FORBIDDEN` bodies instead of empty statuses for API callers. |
| Redaction | `Redaction` helper masks e-mail/phone/secret values before they are persisted or logged. Authentication audit summaries store `o***@domain` plus a reason code; the development password-reset ticket is returned in the response body only and the log records that a ticket was generated — never the token. Session cookies, passwords and authorization headers are never logged or echoed in errors. |
| Structured audit | Login success/failure (`login.succeeded`, `login.failed` with `invalid-credentials`, `unknown-or-inactive`, `setup-required`, `locked-out`) are recorded in the append-only `audit_events` table with user/business, timestamp, masked identifier and the request correlation id. New `GET /api/v1/audit-events` feed (filters: `entityType`, `action`, `userId`, `from`, `to`; keyset paging) exposes business entries plus the caller's own authentication events only; protected by the new `audit.view` permission (Owner). Business document audit rows were already written inside the same transaction as the change they describe. |
| Real PostgreSQL backup/restore | `scripts/backup-postgres.ps1` (custom-format `pg_dump`, SHA-256 sidecar manifest), `scripts/restore-postgres.ps1` (digest verification, refuses the live database name, requires `-Force` to replace a target), `scripts/restore-drill.ps1` (backup → restore into `qtsbilling_restore_drill` → reconcile table counts, identity users and posted journal debit/credit totals → drop the disposable database; fails on any mismatch or SQL error). No backup metadata row is treated as a backup. |
| Least-privilege DB roles | `scripts/provision-postgres-roles.ps1` creates a DML-only `qtsbilling_app` role (no DDL/ownership, `PUBLIC` privileges revoked, default privileges for future objects) and proves the boundary: `SELECT` succeeds, `CREATE TABLE` and `DROP TABLE` are refused. |
| Key management | Optional `QTS_DATAPROTECTION_PATH` persists the Data Protection key ring outside the repository/database so session cookies and tickets survive restarts; rotation is documented as a deliberate operation. No custom crypto and no static IV anywhere in the new host (Identity PBKDF2 hashes; Data Protection for cookies/tokens). |
| Server configuration/deployment docs | `docs/migration/deployment.md`: runtime settings, failure model, role/credential rotation, backup and restore policy, logging/redaction rules, secret hygiene and the SQLite device-local protection/recovery policy (OPEN-8 interim). |
| Secret/config static scan | `scripts/secret-scan.ps1` scans every tracked file for connection-string passwords, private keys, static-IV AES usage and hardcoded API keys/tokens; only documented development fixtures are allowlisted. `backups/` is git-ignored. |

## Legacy items mapping

| Legacy concern | Resolution in the new host |
|---|---|
| `ExceptionService.cs` recursive database-error logger | No database-writing logger exists. Audit rows are written transactionally by the action itself; authentication events are separate inserts. Error handling is a response-time middleware only. |
| `SystemUtilitiesService.cs` backup/restore/log sections | Replaced by the three PostgreSQL scripts above and the `.NET` logging pipeline; backup metadata is never mistaken for a backup. |
| Duplicate `EncryptionService.cs`, static-IV AES | Not ported. New host uses ASP.NET Core Identity password hashing and Data Protection; the scan fails on any static-IV AES usage. |
| Server configuration/deployment documentation | `docs/migration/deployment.md`. |

## Decisions recorded

- **D-43** — security/failure/audit model: typed ProblemDetails for every API failure (`code` + `traceId`),
  no database-writing error logger (logging is best-effort and cannot recurse or fail a request), redaction
  before persistence/logging, authentication audit in append-only `audit_events` with masked identifiers and
  correlation ids, tenant-scoped audit feed (`audit.view`, Owner only), Data Protection key-ring persistence
  via `QTS_DATAPROTECTION_PATH`, real `pg_dump` backups with SHA-256 manifests and a recurring restore drill,
  and a DML-only application DB role with no DDL/ownership. Development fixtures (dev DB password, seeded
  owner) are explicitly allowlisted by the static scan and forbidden in deployment.
- **D-44** — device-local SQLite policy (OPEN-8 interim): sandbox + OS-level protection minimum, WAL and
  `PRAGMA integrity_check`, pre-upgrade snapshot, quarantine/re-initialize/re-sync on corruption, provisional
  queue retained until server acknowledgement, sandbox wipe on sign-out/retirement; final at-rest encryption
  choice remains OPEN-8 and no card/CVV data is ever stored on the device.

## Not included (tracked)

- A custom crypto framework, at-rest encryption for the server database beyond volume/OS controls, or an
  external secret manager integration — deployment concerns outside this task.
- Final SQLite encryption selection (OPEN-8) and the device implementation itself (QB-18/19/20 blocked by
  the missing `maui-windows` workload).
- Backup scheduling/retention automation on the deployment platform — the scripts and drill are provided;
  the schedule is an operational setting documented in `deployment.md`.
