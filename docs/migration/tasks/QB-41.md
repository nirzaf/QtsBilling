# QB-41 — The native authorization-code + PKCE identity (specification task 22)

**Status: DONE (the flow is live and proven against the real PostgreSQL).** The Windows public client
no longer copies a browser cookie: it opens the system browser, receives an authorization code at a
registered loopback redirect and exchanges it with a PKCE verifier. Task 23 (the signed offline grant)
is the remaining part; this slice issues and validates the online access token.

## What was built

| Piece | Where | Behaviour |
|---|---|---|
| The authorization store | `QtsBilling.Persistence.Postgres/BillingDbContext.OpenIddict.cs` + `20261020135819_AddNativeAuthorizationStore` | Applications, authorizations, scopes and tokens live in PostgreSQL. The token payload and the JSON collections are `text`; the business 400-character convention does not truncate them. |
| The server | `QtsWebApp/QtsWebApp/Program.cs` | Authorization-code **and** refresh-token flows; PKCE (S256) is required server-wide and on the client; the token, revocation and discovery endpoints are OpenIddict's own. |
| The client | `Feature/Auth/NativeAuthorizationEndpoints.cs` | One public client, `qts-windows`, with two loopback redirect addresses and **no secret**. The client cannot opt out of PKCE. Registration is idempotent. |
| The authorization endpoint | `Feature/Auth/NativeAuthorizationEndpoints.cs` | Requires the browser session cookie; validates the client, the redirect address, the code response, S256 and the state; refuses a session without an active business; signs in a principal that carries the subject, the name and the business scope, **never the permissions**. |
| The schemes | `Program.cs` | A policy scheme selects **one** scheme per request: a `Bearer` header selects the OpenIddict validation handler, otherwise the Identity cookie. The principals are never merged. |
| Key custody | `Program.cs` | Development and Testing use the development certificates. Every other environment **fails closed** unless `QTS_OPENIDDICT_CERTIFICATE_PATH` names the reviewed signing certificate. |

## The evidence (all against real PostgreSQL, `TestQtsBilling/Integration/NativeAuthorizationTests.cs`)

| Test | Proves |
|---|---|
| `T22_01_discovery_and_the_authorization_code_flow_with_pkce` | Discovery advertises the endpoints and S256; a real cookie session obtains a code; the code plus verifier yields tokens **without a client secret**; the bearer token reaches `/api/v1/customers` on a client that shares no cookie with the browser; the refresh token is single-use and its replay is `invalid_grant`. |
| `T22_02_a_wrong_verifier_and_a_replayed_code_are_refused` | A wrong verifier is `invalid_grant`; a code redeemed once cannot be redeemed again. |
| `T22_03_the_authorization_endpoint_requires_the_signed_in_membership` | No session means no code (a redirect to the sign-in page); an unregistered redirect address is a `400`. |
| `T22_04_the_access_token_loses_authority_when_the_membership_is_revoked` | A valid token for a user whose membership was just revoked is authenticated but **forbidden**: the permission handler reads the current membership, so the token never caches authority. |

The whole suite passes: **94 tests** (90 before this slice), and the cutover safety still passes 14/14.

## What is deliberately absent

- No password grant, no client secret in the desktop binary, no external identity provider.
- No offline grant yet: that is task 23, tracked as finding F10 and still **NOT EXERCISED** in the
  readiness ledger.
- Production certificates and the issuer are infrastructure decisions (BLOCKED_EXTERNAL); the host
  refuses to start in production without the signing certificate.
