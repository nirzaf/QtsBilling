# QB-22 — MAUI push/pull coordinator and conflict-resolution queue

**Status: DONE (device loop, conflict queue, background run).** The desktop client now synchronizes: it
pushes the operations it captured offline to `POST /api/v1/sync/operations`, stores the receipt, pulls the
change feed into its local cache, and keeps a queue of conflicts for the operator when a server change
touches a record a pending local operation also uses. The loop runs in the background every minute and on
demand from the point-of-sale screen, and it never deletes anything on the device: a refused operation
stays in the queue for the operator, a change that collides with a pending operation becomes a conflict
instead of overwriting the local value.

## Deliverables

| Area | What was delivered |
|---|---|
| Contracts | `QtsBilling.Contracts/Sync`: `ISyncCoordinator` (run / push / pull / status), `ISyncConflictService`, the device DTOs (`SyncStatus`, `SyncRunReport`, `SyncConflict`, `SyncConflictResolution`) and `ISyncApiClient` with the typed push and feed calls. The browser host has no local queue, so it registers no coordinator. |
| Device coordinator | `QtsBilling.Maui/Services/DeviceSyncCoordinator.cs`: the push reads the due outbox rows, builds the envelope from the stored canonical payload (the same payload the server fingerprints), stores the receipt and counts the outcome; the pull walks the feed from the stored cursor, applies the projections to the cache and moves the cursor. A `RESYNC_REQUIRED` answer wipes the cache and re-pulls the baseline. |
| Conflict queue | The store applies a change only when no pending local operation uses the record; otherwise it writes a `sync_conflicts` row with the server value, the local value and the reason, and the operator resolves it with **use server** or **keep local** (the local operation then stays authoritative). The new table is a third SQLite migration of the device store. |
| Background loop | `DeviceSyncTimer` runs the coordinator every 60 seconds; MAUI does not start hosted services on its own, so the window starts the timer explicitly. A failed run is swallowed - the queue keeps the work. |
| Device status | The point-of-sale screen shows the device sync card: online/offline, how many operations wait, how many conflicts are open, the feed revision and the last successful pull, plus a **Sync now** button. The pending queue shows the outcome per operation (`Pending sync`, `Posted`, `Rejected`). |
| Server answers | The pushed operation is answered by the QB-20 handler; a rejected operation (another business, the same key with another body) is remembered by the device as terminal, so it is not retried forever. |
| Store safety | The catalog refresh now rebuilds the cache and re-resolves the location and the cash register against the server, so a device that was enrolled to another business cannot keep its old rows or its old location. |

## Legacy items mapping

| Legacy concern | Resolution |
|---|---|
| The desktop client had no way to send or receive anything | The outbox is pushed and the change feed is pulled; the local cache follows the server. |
| A local sale could be silently overwritten by a server change | The conflict queue holds the decision for the operator. |
| The client retried operations forever | A terminal refusal is recorded and the operation stops being retried. |

## Decisions recorded

- **D-51** — device synchronization loop (QB-22): the device pushes its local outbox and pulls the
  change feed; the loop never deletes anything on the device and never resolves a conflict silently. A
  refused operation (another business, or the same key with another body) is terminal and is kept for the
  operator instead of being retried forever; a server change that touches a record a pending local
  operation uses becomes a conflict with both values, and the operator decides - the device never lets the
  server overwrite a pending local sale. A `RESYNC_REQUIRED` answer wipes the cache and re-pulls the
  baseline, so a device that fell behind re-syncs instead of drifting. The catalog refresh rebuilds the
  cache and re-resolves the location and the cash register against the server, so a device that was
  enrolled to another business cannot keep its old rows.
