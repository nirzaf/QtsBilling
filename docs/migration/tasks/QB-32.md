# QB-32 — A safe PostgreSQL/API regression harness and the native readiness ledger

**Status: DONE (the harness runs the real host against a disposable PostgreSQL 18 and the four safety
cases pass).**

This is task 01 of the *SMB Completion and Production Hardening* specification. It is the foundation
every later financial claim stands on: a harness that can touch a production database, or whose
assertions can be satisfied by a global cancellation, makes every later test worthless.

## What was built

| File | What it does |
|---|---|
| `TestQtsBilling/Integration/PostgresApiFixture.cs` | A disposable fixture: it creates its own random `qts_test_…` database on an explicitly allowlisted server, applies the real migrations, marks the database with a fixture marker, runs the **real host** against it and drops the database afterwards. It never falls back to the production connection, never uses a database whose name is not a test name, and only ever removes a database that carries its own marker. It seeds two businesses with deliberately similar SKUs and account codes, plus the five identities (owner A, owner B, cashier, viewer, deactivated). |
| `TestQtsBilling/Integration/FinancialAssertions.cs` | The financial assertions: the state capture (debits, credits, stock, payments, audit, entries), the **per-entry** balance check, the document check (the header totals equal the sums of their own lines and the revenue base is the payable minus the tax inside it) and the before/after comparison. |
| `TestQtsBilling/Integration/HarnessSafetyTests.cs` | The four safety cases T01.01 – T01.04 (see the evidence). |
| `QtsWebApp/QtsWebApp/Program.cs` | The host reads its connection string from the configuration, so the test host can point the same code at its own database. The environment variable keeps the precedence in every real deployment, and the entry point is visible to the test host. No production bypass was added. |
| `.github/workflows/ci.yml` | The CI now runs the real PostgreSQL 18 service and executes the integration suite with it. The production connection variable is never set in the workflow. |
| `docs/migration/readiness.md` | The native readiness ledger: the gates, the eighteen requirements, the critical reproductions (exercised or not) and the external blockers. |

## The safety rules (T01.01)

The fixture refuses, **before** it opens a privileged connection:

- a database that is neither the maintenance database nor a `qts_test…` name;
- a host that is not on the allowlist (`localhost`, `127.0.0.1`, `::1` by default, extendable with
  `QTS_TEST_POSTGRES_ALLOWED_HOSTS`);
- the production connection string itself;
- a missing `QTS_TEST_POSTGRES_CONNECTION`: the tests then **fail** with that message. A missing
  prerequisite is never reported as a pass, and there is no skip that would hide it.

## The evidence

| Case | Result |
|---|---|
| T01.01 — a production-shaped connection | EXERCISED: the production database name, a remote host and the production connection string are each refused before any DDL. |
| T01.02 — a cross-business resource | EXERCISED: the owner of business A posting a line of business B against business A's own location is refused (not `201`), and the exact financial state of **both** businesses is unchanged afterwards (debits, credits, stock, payments, audit rows, journal entries). |
| T01.03 — an exception before the commit | EXERCISED: an audit row is written inside a transaction that is rolled back; the financial state is byte-identical afterwards. |
| T01.04 — a global cancellation | EXERCISED: an entry of `DR 115 / CR 100` next to a compensating `CR 15` entry fails the per-entry assertion — the cancellation elsewhere never hides the broken entry. |

The suite runs against a real PostgreSQL 18 with the real migrations, the real locking and the real
constraints — never against a mock and never against EF InMemory. Migrations and fixture setup use the
separate `QTS_TEST_POSTGRES_CONNECTION`; the API host uses `QTS_TEST_POSTGRES_RUNTIME_CONNECTION` and
connects with the DML-only role. The fixture grants that role access only to its random database and
clears that database's connection pools before dropping it, so cleanup does not require `pg_signal_backend`.

## How to run it

```powershell
# the disposable test server (the fixture creates and drops its own database)
$env:QTS_TEST_POSTGRES_CONNECTION = "Host=localhost;Port=5433;Username=qtsbilling;Password=qtsbilling;Database=postgres"
$env:QTS_TEST_POSTGRES_RUNTIME_CONNECTION = "Host=localhost;Port=5433;Username=qts_app;Password=qtsbilling;Database=postgres"
dotnet test TestQtsBilling/TestQtsBilling.csproj -c Release
```

Without the migration variable the integration cases fail with a clear message. CI provisions both roles
and sets both connection variables before the tests.

## Decisions recorded

  PostgreSQL 18 on an allowlisted host, in a random `qts_test_…` database that the fixture creates and
  removes itself; a production-shaped target, a non-allowlisted host, the production connection
  string and a missing prerequisite are all refused before any privileged connection; the assertions
  are per entry, per document and per business, so a global cancellation can never satisfy them.

  per gate, what is implemented, what is verified and what is missing. A task document marked "done" is

  real stack.
