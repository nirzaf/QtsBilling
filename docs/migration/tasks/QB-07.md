# QB-07 — Replace journals with balanced, immutable ledger

**Status: DONE (verified live on PostgreSQL 18.6).** Posted journal entries are immutable, balances are
derived from posted lines only, closed periods reject posting, and one source reference can produce at most
one business effect (F-03/F-04/F-11).

## Deliverables

| Area | Contents |
|---|---|
| Chart of accounts | `GET/POST /api/v1/accounts`, `PUT /api/v1/accounts/{id}`; per-business unique `code`, parent hierarchy with cycle guard, deactivation instead of deletion. |
| Periods | `GET/POST /api/v1/accounting-periods`, `POST /{id}/close`; non-overlapping ranges, posting into a non-open period returns `409 ACCOUNTING_PERIOD_CLOSED`. |
| Posting | `POST /api/v1/journal-entries` posts one balanced entry atomically: ≥ 2 lines, exactly one side per line, equal debit/credit totals, scale ≤ 4 decimals, active accounts of the same business, business base currency. |
| Immutability | Entries are inserted directly as `posted`; no update path exists. `POST /api/v1/journal-entries/{id}/reverse` writes a new swapped entry referencing the original and leaves it untouched; a second reversal is refused. |
| Idempotency | Unique partial index `ux_journal_entries_business_source` on `(business_id, source_type, source_id) where source_id is not null` plus a pre-check: a replayed source reference returns `409 IDEMPOTENCY_KEY_REUSED`. |
| Numbering | `invoice_sequences` row locked `FOR UPDATE` inside the posting transaction (`JE-<year>-00001`): concurrent posts cannot duplicate numbers and a rolled-back post consumes no number (QB-11 reuses the table for invoices). |
| Derived balances | `GET /api/v1/reports/trial-balance?from&to` aggregates **posted lines only**; no stored balance column exists anywhere (F-11). |
| DB guards reused | The deferred balance trigger, append-only rules, single-sided-line check and period/account FKs from QB-03 remain the last line of defence if service validation regresses. |
| Transactions | Posting and reversal run inside `CreateExecutionStrategy()` so the Npgsql retrying strategy can retry the whole unit; each retry starts from a cleared change tracker. |

## Evidence (live host + PostgreSQL 18.6, `docs/migration/tasks/qb07-evidence.txt`)

| Check | Result |
|---|---|
| Seeded chart of accounts | `GET /api/v1/accounts` → 11 accounts (`1000`…`5100`) |
| Balanced manual post | `201`, `JE-2026-00001`, `totalDebit=100 totalCredit=100` |
| Unbalanced post | `400 UNBALANCED_JOURNAL` (`detail: "Total debits (100) must equal total credits (90)"`) |
| Zero-sided line | `400 VALIDATION_FAILED` (`lines[0]` field error) |
| Source replay (`origin=sale`, same `sourceId`) | first `201`, replay `409 IDEMPOTENCY_KEY_REUSED` |
| Reversal | `201` (`JE-2026-00003`, `reversalOfEntryId` = original); original read back `status=posted`, memo/intact totals unchanged |
| Second reversal | `409 IDEMPOTENCY_KEY_REUSED` |
| Trial balance | 2 rows, `totalDebit=250 totalCredit=250`; cash 150/100 → 50, sales 100/150 → −50 |
| Closed period | posting dated inside a closed FY 2027 period → `409 ACCOUNTING_PERIOD_CLOSED` |
| Cross-business id | `404 NOT_FOUND` |

## Deliberate scope choices

- Drafts are not exposed: the API posts completed entries (the `draft` status remains for imported legacy rows).
- Multi-currency journals are rejected with a field error; revaluation/inflation accounting is a later business decision.
- Reversal uses the original entry date, so reversing inside a closed period is impossible by construction.
- The dev host seeds a starter chart of accounts, the current fiscal year and the journal series; production
  chart setup remains an explicit onboarding step (QB-27 runbooks).
