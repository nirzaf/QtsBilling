# QB-43 — Posted documents freeze, and history cannot be rewritten (specification task 09)

**Status: DONE and EXERCISED against real PostgreSQL.** Findings F17, F19 and F32 are closed in
`readiness.md`. Every refusal below was driven by raw SQL against the real database, so it proves the
trigger and not a handler that a different code path can bypass.

## What was built

| Piece | Where | Behaviour |
|---|---|---|
| Invoice header guard | `20261020145343_HardenPostedDocumentGuards` | Invoices are created as drafts. The financial terms (customer, dates, currency, subtotal, discount, tax, total, note) freeze when the invoice leaves draft; only `status`, the payment snapshot and the row version may change. Only known statuses are accepted; a delete is refused; an invoice with no lines or a header total different from its line sum cannot be issued. |
| Invoice line guard | same migration | A line can only be inserted while its parent is draft; an existing line can only change while **both** its old and new parent are draft (so a line cannot be moved out of an issued invoice); a delete is refused after issue. |
| Purchase-order guard | same migration | A PO is created as a draft; header terms freeze from `Ordered` on; after that only `quantity_received` and its timestamp may change (partial receiving), and only known statuses are accepted. Closing/cancelling cannot rewrite the terms. |
| Sale, payment and journal guards | same migration | A posted sale, a confirmed payment and a posted journal entry are append-only: their amounts, dates, currency and identifying facts cannot change, and they cannot be deleted. Statuses are restricted to their known values, so a row cannot be rewound to draft. Journal lines can only be inserted while the entry is draft. |
| Bulk erasure | same migration | `TRUNCATE` on the append-only history (`audit_events`, journal and sale history) is refused, so an operator cannot bypass row triggers with a bulk statement. |
| Ledger writer | `Features/Accounting/LedgerWriter.cs` | Saves the entry as `Draft`, adds its lines, then marks it `Posted` in the same caller-owned transaction. The deferred balance trigger still evaluates at `COMMIT`, so a broken entry can never be committed. |

## The evidence (against real PostgreSQL)

`TestQtsBilling/Integration/PostedInvariantTests.cs`:

| Test | Proves |
|---|---|
| `T09_01_an_issued_invoice_rejects_headers_lines_moves_and_deletes` | A header total change, a line quantity change, a line insert, a line move into a draft (the **old** parent is checked), and a delete are each refused with `23514`; the document still has its one line and its issued total. |
| `T09_03_the_issue_transition_requires_lines_and_a_matching_total` | A draft whose header total no longer matches its lines cannot be issued; an empty draft is refused by the API with `409`; an issued invoice cannot be rewound to draft. |
| `T09_04_posted_money_and_journal_facts_are_immutable` | A posted sale, its confirmed payment and a posted journal entry refuse amount/date changes and deletes; a line insert into a posted entry is refused; the entry is still balanced at 10/10. |
| `T09_05_append_only_history_cannot_be_truncated` | `TRUNCATE audit_events` and `TRUNCATE journal_entries CASCADE` are refused. |
| `T09_06_the_guards_can_be_reverted_and_reapplied` | On a disposable database the migration reaches the new schema, both `Down` methods restore the previous draft-only line triggers, and both `Up` methods apply again. |

The whole suite passes: **107 tests** (98 before Tasks 09/10; 106 before the migration test).

## What remains

- Task 09 is about the database-level freezing; the API's own final-state rules are exercised only where
  these tests drive them (issue and posting). A dedicated final-state matrix for every document
  transition is not claimed here.
- Historical documents written before this migration are not rewritten or repaired; the guard applies
  to every future write (D-72).
