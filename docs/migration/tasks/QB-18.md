# QB-18 — .NET MAUI Windows Blazor Hybrid application

**Status: DONE (Windows desktop host built, started and driven on Windows 11; the web host stays
independently deployable).** The `maui-windows` workload is installed, so the desktop client is real:
`QtsBilling.Maui` is a .NET 10 MAUI Blazor Hybrid app for `net10.0-windows10.0.19041.0` that hosts the
**shared** `QtsBilling.Ui` components in a WebView2, opens the device-local SQLite store from QB-17,
authenticates against the same server API as the browser without embedding a credential, and starts and
stays usable while the server is unreachable. The port also uncovered a real defect in the shared
customer page (the loaded rows were never re-rendered), which is fixed here and verified in both hosts.

## Deliverables

| Area | What was delivered |
|---|---|
| New project | `QtsBilling.Maui` (`Microsoft.NET.Sdk.Razor`, `UseMaui`, `net10.0-windows10.0.19041.0`, Windows only - Android/iOS/macOS are explicit non-goals). It references `QtsBilling.Ui` (shared UI), `QtsBilling.Contracts` (wire contracts) and `QtsBilling.Persistence.Sqlite` (device store), and owns MudBlazor 9.11.0 as a host asset. The template demo pages (Counter/Weather), the bootstrap assets and the non-Windows platform folders were removed. |
| Shared components in the desktop app | `Components/Routes.razor` registers the RCL assembly in `AdditionalAssemblies` and uses `QtsBilling.Ui.Layout.MainLayout` as the default layout, so the customer page, the dialog, the layout and the navigation menu are the *same* components as in the browser - no duplicated markup. |
| Host-owned assets | `wwwroot/index.html` loads the MudBlazor CSS/JS and the shared scoped CSS bundle (`_content/QtsBilling.Ui/QtsBilling.Ui.bundle.scp.css`); the RCL never loads host assets. |
| Host shell | `MainPage` hosts the `BlazorWebView`; the host owns the Home page (device identity, server address, connectivity) and the Sign-in page. Both are host concerns and are not duplicated into the shared library. |
| Device identity | `DeviceIdentity` generates a GUID v7 on first start and keeps it in the application preferences - the device id used by the sync protocol and by the server's device authorisation. |
| Secure session | `SessionStore` keeps the session cookie and the last known session summary in the platform **secure store** (DPAPI on Windows), never in plain preferences and never in the package. `SessionAuthHandler` attaches the stored cookie to every API call and captures the rotated cookie. |
| Offline-tolerant API | `DeviceAccountApiClient` / `DeviceCustomerApiClient` reuse the shared contract clients and only translate a transport failure into the typed `ApiException` (`STORE_UNAVAILABLE`), so a shared component shows a readable message instead of an unhandled exception. `GetSessionAsync` falls back to the cached session, which is what lets the app start offline. |
| Device-local store | The app opens the QB-17 store at `%LOCALAPPDATA%\<app>\Data\qtsbilling\local.db` before any UI data is requested: integrity check, compatibility check, WAL, migrations, crash recovery. |
| Connectivity & diagnostics | `DeviceConnectivity` reports the OS network state; `StartupDiagnostics` writes a secret-free startup report (device id, server address, local-store schema/WAL/integrity, shared routes) and `DeviceApiLog` appends method/route/status/duration for every API call (no credential, cookie value or payload body). |
| MSIX configuration | `Platforms/Windows/Package.appxmanifest` carries the real identity (`com.qtsbilling.desktop`), display names and the desktop device family; the local build runs unpackaged (`WindowsPackageType=None`) so the app can be smoke-run, and MSIX packaging/signing stays with QB-27. `app.manifest` keeps per-monitor v2 DPI awareness. |
| Shared-component defect fixed | The shared customer page loaded its rows but never re-rendered them (the load starts in `OnAfterRenderAsync`, where Blazor does not re-render by itself), so both the browser and the desktop app showed an empty grid with a permanently busy button. `Customers.razor.cs` now calls `StateHasChanged()` after the load; the dead `SearchCustomersOnInput` handler was removed. Verified in the browser (6 rows, "1-6 of 6") and on the desktop (6 rows). |
| Secret hygiene | The desktop client embeds no credential: the operator types the sign-in, the session lives in the DPAPI secure store, and the repository-wide static scan (236 tracked files, including the new project) is clean. |

## Legacy items mapping

| Legacy concern | Resolution |
|---|---|
| WinForms desktop client against a central database | The MAUI host is a separate application that talks to the same server API; the legacy WinForms app is untouched until QB-29 (gated). |
| Duplicated UI between browser and desktop | Both hosts render `QtsBilling.Ui`; only the shell, the assets and the session UX differ. |
| Credentials stored on the device | Only the session cookie (DPAPI) and the device id live on the device; no password, token or card data is stored. |
| Device data in unknown state | The local store is created and migrated by the app itself, with the QB-17 integrity/compatibility checks and a startup report for support. |

## Decisions recorded

- **D-47** — desktop host boundary (QB-18): `QtsBilling.Maui` is a Windows-only MAUI Blazor Hybrid host
  that owns the shell, the host assets, the device identity, the secure session and the device-local
  store, and renders the shared `QtsBilling.Ui` components unchanged. The desktop client never embeds a
  credential: the operator signs in against the same server API and the session cookie lives in the
  platform secure store (DPAPI on Windows), so a restart keeps the device signed in. Transport failures
  are translated into the typed `ApiException` (`STORE_UNAVAILABLE`) at the host boundary, and the session
  falls back to the last known one, so the app starts and stays usable while the server is unreachable.
  The device writes a secret-free startup report and an API-call log for support. The `maui-windows`
  workload is now installed, so the blocker recorded in D-25 is resolved and QB-19/QB-22 can consume this
  host.
