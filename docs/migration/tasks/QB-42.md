# QB-42 — The signed offline capture grant (specification task 23)

**Status: PARTIAL — the server half and the shared validator are DONE and EXERCISED; the native
enrolment challenge and the device-side capture gate are implemented but NOT EXERCISED.** Finding F10
stays **partially proven** in `readiness.md`: the cached session summary no longer looks like authority
in the device code, but no test has yet driven the MAUI host through an offline capture. Not claiming
otherwise.

## What was built

| Piece | Where | Behaviour |
|---|---|---|
| The grant format | `QtsBilling.Contracts/Identity/OfflineGrant.cs` | RSA-SHA256 compact JWT. Issuer, audience, version, user, device, business, location, optional register session, currency, frozen permissions, authorization revision, issue/expiry. Lifetime 8 hours; 24-hour maximum. |
| The signer | `QtsWebApp/QtsWebApp/Features/Devices/DeviceEndpoints.cs` (`OfflineGrantKeyRing`) | One key per process. Development/Testing generate an ephemeral key; every other environment fails closed unless `QTS_OFFLINE_GRANT_PRIVATE_KEY_PATH` names the reviewed PEM key. Signing is serialized because one `RSA` instance is not safe for concurrent use. |
| Enrolment | `POST /api/v1/devices` | Owner/manager (`devices.manage`), current business, location must belong to that business. The database composite key refuses a cross-business location even if the endpoint forgets. |
| Issuance | `POST /api/v1/devices/{id}/offline-grant` | Requires `sales.post`; loads the active device of the current business; refuses a revoked device with `409`; refuses a location that is not the device's; refuses a closed/foreign register session; freezes the caller's role permissions and the current membership revision. |
| The public key | `GET /api/v1/devices/offline-grant-key` and the issue response | The device pins the key id and public key at first issue. The private key never leaves the server. |
| The device gate | `QtsBilling.Maui/Services/OfflineGrantService.cs`, `SessionStore.cs`, `DeviceLocalPosService.cs` | The capture path requires a stored, unexpired grant validated on the device. The session summary is no longer authority. A pin mismatch (`key_changed`) refuses capture; a clock rollback is refused and is never repaired by contacting the server. Sign-out clears the grant but keeps the pinned key. |

## The evidence (against real PostgreSQL)

| Test | Proves |
|---|---|
| `T23_01_a_grant_is_signed_and_bound_to_one_device_business_and_location` | The published key matches the issuing key; a valid grant names the device/business/location/user; a grant presented as another device is refused (`binding`); an expired grant is refused; a rolled-back clock is refused (`clock_rollback`); a one-character signature change is refused. |
| `T23_02_a_revoked_device_never_receives_another_grant` | A revoked device gets `409`; a cashier (not owner) can still obtain a grant for their own device, bounded by their own membership. |
| `T23_03_a_location_of_another_business_is_refused_by_the_api_and_the_database` | The API returns `400` and writes nothing; a raw SQL insert with another business's location is refused by PostgreSQL with `23503`. |
| `TestQtsBilling/Identity/OfflineGrantTests.cs` | The pure round-trip and all four refusals (wrong device, expired, clock rollback, altered signature) without a host. |

The whole suite passes: **98 tests** (94 before this slice).

## What remains (and why F10 is not closed)

1. **One-time enrolment challenge**: enrolment currently authenticates the owner/manager and validates
   the location, but there is no short-lived challenge that the enrolling device must present. A stolen
   owner cookie could enrol a device during its lifetime.
2. **Register-session binding on the device**: the grant supports it and the server validates an
   optional session, but the MAUI capture path passes `null`; the device's register id is not a
   cash-register session id.
3. **The device gate has no automated test**: SecureStorage and the MAUI host are not driven by the test
   suite; only compilation is proven. The G7 platform check (real Windows certificate/browser callback)
   remains an external gate.
4. **Key rotation procedure**: a new key id refuses capture until the device is deliberately re-enrolled;
   that operational runbook does not exist yet.
